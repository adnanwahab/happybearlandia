# Causal SQLite storage

`createCausalStore(db)` in `storage.js` attaches additive, transactional migrations to an existing Bun SQLite connection. `createWorldPersistenceStore(path).causality` exposes it on the authoritative world store connection; close the world store to close that connection. No separate world-state database is created.

Create a run with `createRun(context)` using canonical `RunContext`. The result is `{id,context,status,revision}`. Optional metadata can be supplied with `createRun({context,metadata})`; allowed metadata keys are `manifest`, `metricDefinitions`, `provenance`, `interventions`, and `distributions`. Metadata is finite JSON preserved verbatim and included in the terminal hash. Append with `commitStep(runId, {expectedRevision, events, observations, assumptions, edges, checkpoints})`. All arrays are optional and bounded to 10,000 records. Every record uses the shared runtime schemas, preserving provenance and canonical contexts. Events, observations and assumptions share a unique, monotonically appended sequence namespace. Their ticks must be nondecreasing by sequence. A successful transaction advances the revision once; any failure rolls the whole step back.

Dependencies (`causes`, `contributes`, `constrains`) require existing same-run endpoints with strictly increasing sequence and nondecreasing tick. This ordering guarantees an acyclic dependency graph. `correlates` edges are associations and may point backward. Evidence IDs must resolve to same-run nodes. Checkpoints use the shared checkpoint contract, whose `hash` must equal `causalContentHash(state)`; they record replay state, never replace an authoritative live world. Parent runs must exist and share universe/world/scenario scope.

`getRun`, `getNode`, `listRuns`, `listEvents`, `listObservations`, `listAssumptions`, `listEdges`, and `listCheckpoints` read stored records. Lists return `{items,nextCursor}`. Defaults are 100 rows, maximum 1000. Node/checkpoint cursors use `afterSequence`; run/edge cursors use `afterId`. Edge filters accept `sourceId`, `targetId`, `association`; run filters accept `universeId`, `worldId`, `scenarioId`, `status`. Pass the returned cursor as the appropriate next `after*` argument. Returned records include computed `contentHash`.

`completeRun(runId,{expectedRevision,status:'completed'})` seals a run; `failed` also seals it. Canonical SHA-256 hashes exclude JSON key insertion order; terminal run hashes include context, status, revision, and all record hashes sorted by table and ID. Database triggers prevent terminal run mutations, and record updates are always forbidden. There is no public delete operation. Schema migration version is stored in `causal_storage_migrations`; repeated initialization preserves existing records.

Storage is server-only (Bun SQLite and Node crypto), separate from the browser-safe `index.js` exports. This layer provides no HTTP authorization; callers must enforce request policy before invoking writes.
