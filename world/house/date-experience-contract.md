# Date experience helpers

All state is stored on the existing active `date.experience`; helpers create no residents, registries, clocks, or simulation worlds. Initialize with `createDateExperience({date, minute})`. Dates require actual `personIds`, venue, phase, startedMinute and untilMinute.

Call `advanceDateExperience(date, {minute, actor, partner, relationship, nearbyPlaces, budget, weather})` only for the current active date while actual participants remain assigned. It generates opportunities every five simulated minutes and seeded events every fifteen; it returns `{events,effects}`. Apply each returned effect exactly once as part of the same authoritative model transaction. Missed tick intervals coalesce to one opportunity/event, so checkpoint restoration and large steps remain bounded. Events are seeded from date ID and authoritative minute. Context actor/partner are transient views of actual population residents: `{name, traits, interests, needs, preferences}`. Get canonical personalities through `datePreferencesFor(model,personId,learned)`; do not create replacement characters. Persist learned history on existing date/relationship memories, and pass it to future date preference calculations. `inspectDatePreferences` exposes only discovered categories.

Commands: `applyDateExperienceCommand(date,input,context)` with mandatory stable bounded `commandId`; use `type: conversation` + `choiceId`, `travel` + `optionId`, `opportunity` + current `opportunityId` + `response` (accept/later/decline), `minigame-start` + `gameType`, `minigame-input` + `action`, or `minigame-complete`. Replaying a command returns empty `effects`, preventing duplicate cash/need/relationship/skill grants. Invalid commands do not mutate state. The integration must check actual active date, both actual adults' existing consent/attendance, and canonical affordability before invoking commands; paused commands never advance the simulation clock. Effects contain bounded need deltas for both participants, shared `cost`, `delayMinutes`, relationship deltas, discoveries and skills. Partner opportunities return a destination/suggestedAction only; accepting does not automatically transport, extend, or end a date. Integration handles those through existing authoritative lifecycle and place commands.

Playable games require a supported current venue and no active shared activity/travel. Karaoke lane and arcade direction inputs are integers 0–3; golf uses power 0–1 and aim -1–1. `inspectDateMinigame` supplies current challenge and next input minute. Every turn requires at least 0.5 simulated minutes per elapsed round; karaoke/arcade have eight turns, golf three. Scores are derived exclusively from stored bounded inputs, never client scores. Complete only after all turns; skills and relationship effects appear only at completion. Skill minute keys are canonical creativity, logic, and fitness. The model owner applies those to each actual participant's owning household progression, avoiding ownership violations for visiting partners. Ending/traveling cancels or abandons partial games with no completion rewards.

`inspectDateExperience(date)` omits command receipts. `validateDateExperience(date)` and `validateDateMinigame` validate checkpoint state and score/input consistency. Logs retain 96 events, receipts 128 commands, learned experiences 64, completed games 12. Receipt capacity rejects further commands instead of evicting replay protection. Ranking helpers return normalized scores plus explicit preference, novelty, budget and route explanations; approximate routes remain labeled.
