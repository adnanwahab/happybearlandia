# Date recipe UI integration

`mountDateRecipes(container,{onCommand,onDateCommand,onAdventure,onConversation})` exposes `update({recipes,people,minute})`, `open`, `close`, `destroy`.

Pass `home.systems['date-recipes']` inspector output as `recipes`. The UI uses the actual controller's `plan`, `next`, `rules`, `propose`, `derail`, `resume`, `abandon`, and `open-envelope` types. It adds a fresh bounded `commandId` per explicit click and the actual inspected `dateId`. `onCommand` should send through `runtime.householdSystemCommand({householdId,system:'date-recipes',...input})` and refresh inspection. Results use the canonical `{accepted,result:{proposedCommands,...}}` wrapper. Suggestions never execute automatically. Returned proposals require a second explicit click; `onDateCommand` must use the existing normal dates authority and return `{accepted:true}` only for accepted requests. Travel and activity proposals retain separate availability/arrival checks; rejected/unexecuted proposals remain for retry. A date change invalidates pending review. Rules labelled not verifiable remain visibly so. Pacing use means proposals, not earned events.

`onAdventure()` and `onConversation()` open existing journal/talk UI. Saved photos still use the existing media flow; a photography activity is explicitly not image evidence.

Planner additions are narrow: `mountDatePanel(...,{onRecipeSelected})`, `panel.setRecipeRecommender(fn)`, `panel.getData().recipeSelection`. Supply five canonical recommendations as `data.recipeRecommendations` or `data.recipes.recommendations` (also reads home/house inspector output). A synchronous provider receives `{places,people,personIds,history,minute,budget}`. The backend pure `recommendDateRecipes(model,home)` requires canonical model/home, so the UI does not fabricate a population from inspected people to call it; bind a canonical provider or supply its inspected results.

Selecting an adventure calls `onRecipeSelected({recipeId,title,phase:'planned',personIds,place})` and stores its ID without starting a date or activity. Following an acknowledged actual start it calls again with `phase:'started'` and `result`. Root may instead read `panel.getData().recipeSelection` in its start/save/navigation workflow to issue the recipe `plan` command only after actual date creation and before navigation. No recipe fields are added to the strict existing date start command. Existing four named presets, address selection, consent handling and the fixed Immersive Gamebox address are preserved.

Validation: native tests `test/e2e/date-recipes-ui.e2e.js` cover five cards/all 30 hidden catalogue, unavailable reasons, no execution before review, unchanged fixed Arcade start, and actual canonical controller budget proof and rejected request retention. Existing planner/navigation regressions also pass.
