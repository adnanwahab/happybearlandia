## Current executable boundaries

* `world/house/bridge.js`: saved Living Population household membership is checked
  against the exact prefix/index; a full checkpoint and geometry cross House/World.
  Return validates compatible continuation and creates a child experiment. This
  supplies an existing identity/clock transport, not a retail transaction.
* `world/house/app.js` and `excursion-ui.js`: Go Out uses supplied public location
  IDs and `runtime.walkPerson`, then saves the checkpoint and opens World. Travel
  requires modeled elapsed time. Empty destinations and invalid residents have
  explicit fallback messages. No store stock or purchase is involved.
* `world/house/playable-life.js`: Buy a plant invokes the existing `furniture`
  command. `world/house/model.js` charges 35 synthetic currency units for a plant
  and installs household furniture immediately, with zero elapsed time. It does
  not validate shop arrival, debit retail stock or credit a seller. Repeating
  commands can create further charges; there is no errand transaction key.
* `world/population/economy.js`: Population firm IDs belong to the saved authority,
  but firms use aggregate daily demand/payroll/revenue. There is no plant SKU,
  retail inventory or demonstrated mapping from a public location to its seller.
* `world/business-mode.js`: neighborhood businesses have stock/revenue/costs in a
  different World representation and explicitly reset on reload.
* `world/BUSINESS_LAB.md`: Lab uses a separate daily/monthly ledger in localStorage;
  neighborhood live sales explicitly do not update it. Equal names or coordinates
  do not establish entity identity or a conversion to Population minutes.

These are distinct authorities. Reusing the home furniture button at a shop, or
copying a Business balance into Population, would not satisfy the requested
inventory, clock and no-duplicate guarantees. No synthetic shop or mapping was
silently introduced by this assessment.

## Next integrated implementation slice

Use Population as the authority for one explicitly synthetic retail fixture,
presented in House and World; do not synchronize the unrelated Lab wallet.
First define a versioned public-location → Population seller mapping, plant SKU,
finite stock, price and provenance. Missing mappings must block purchase visibly.
This is a new model contract, not presentation work.

One coding worker should own the shared contract and command before UI work:

1. Persist a bounded errand record with household, resident, destination, seller,
   rules version, start tick/minute, transaction ID and phase in the Population
   checkpoint. Validate actual financial household membership and exact IDs.
2. Start real walk travel; permit purchase only after committed arrival at the
   mapped location. Atomically reconcile household debit, seller credit, stock
   decrement and one owned plant. Persist successful transaction identity so
   retry/reload returns its receipt without another charge. Rejection must leave
   the original model unchanged. Handle capacity/placement failure before debit.
3. Walk home using the same runtime and preserve the full checkpoint through
   existing bridge/session APIs. Both views project that receipt and clock.
   Navigation or autosave failure must retain a retryable transaction result.
4. Add plain keyboard/touch controls and a status region, with no required camera
   animation. Reduced motion and low-end views must retain the complete flow.
   Update Population ODD and linked subsystem contracts beside the rules.

Acceptance evidence still required: deterministic matched-seed round trip and
checkpoint replay; insufficient cash/stock, wrong/missing mapping, non-arrival,
stale requests, double activation, reload/retry and failed-save cases; exact
single debit/credit/stock/object accounting; tick/minute agreement across both
views; normal-entry keyboard and touch/fallback browser tests plus relevant
before/after screenshots. Define bounded receipt retention and behavior when
that bound is reached; eviction must not make an old purchase executable again.

The retail fixture and command can be implemented locally without credentials
or live services. The missing adapter is repository work, not an external-service
prerequisite. Browser prerequisites are a locally resolvable Playwright package,
Chromium and a bind-capable disposable server/database. No approval to deploy or
alter production data follows from this plan.
