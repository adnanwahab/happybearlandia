Read repository AGENTS.md, README.md, docs/design.md, relevant implementation-plan

The design requires source attribution, explicit units and verified mappings
between separately owned models. Current code cannot supply a supported zoning
height envelope on the requested surface:

- `world/gen.js:buildTown` retains OSM building IDs and footprint geometry, but
  does not retain zoning, cadastral parcel IDs or a zoning rules reference. Its
  rendered height is levels times 3.2 metres or a seeded kind-based visual
  assumption. Existing building height is not permission to build that high.
- `world/render.js` consumes those town buildings. The separate
  `world/render/city-renderer.js` also consumes town geometry; its name does not
  establish a Monthly City parcel mapping.
- `world/city/seed.js:createCity` supplies illustrative district parcels with
  `heightLimit:12`. `createCityFromArea` supplies `heightLimit:8` on
  `synthetic-footprint-proxy` parcels. The importer explicitly says zoning is
  synthetic and footprints are not cadastral boundaries.
- Within `world/city`, `heightLimit` occurs only in these seed assignments.
  `contracts.js` does not define or validate its units or rule reference, and
  `systems.js` does not enforce it. The upzone mechanism changes capacity/FAR;
  it cannot be translated into a permitted height without a new assumption.
- `world/buildings/proposal.js` explicitly excludes zoning law validation.
  `world/buildings/world-bridge.js` presents approved project geometry and
  illustrative supply/vacancy mappings, not parcel zoning permissions.
- `/world` first runs `world/renderer-entry.js`; unsupported WebGPU redirects
  to the render-only static city. `world/static-city-model.js` deliberately
  extracts geometry without simulation state or a clock. Both entry paths
  need an explicit overlay contract rather than a hidden model substitution.

No supported enabled case with units, rules provenance and mapped target parcel
was found. Adding arbitrary caps or treating existing heights as zoning would
misrepresent illustrative geometry. A patterned unavailable state is necessary
but alone would not satisfy the enabled-case criterion. Preserve this dependency
rather than declare an unavailable-only overlay complete.

## Next isolated implementation slice

First establish a versioned presentation input, with one owner for its producer
and adapter: authority/world revision, source parcel and building identities,
mapped footprint and coordinate system, supported parameter and units, rule
reference/version, source identity and evidence class, and explicit unavailable
reason. Choose either an honestly labeled synthetic scenario rule with documented
units or a sourced jurisdiction rule; never silently upgrade either into legal
permission. Real zoning additionally needs an authoritative dataset, effective
date, applicable exceptions and parcel mapping. Neither provider nor mapping is
currently supplied by this checkout.

Then implement a bounded read-only overlay module and small host hook, keeping
producer state immutable. Use a stationary translucent envelope visible through
existing geometry; animate opacity on appearance only. Unsupported inputs use a
patterned marker with no numeric permission and no implied vertical bound. Every
numeric height must carry units and a rules reference. Define cleanup, selection
changes and render resource disposal. Provide a native keyboard/touch toggle and
textual selected-parcel status; reduced motion makes appearance immediate.

Acceptance evidence required before completion:

1. A documented supported fixture with a source-bound target footprint, explicit
   height units/rule and expected geometry. Verify unknown/malformed/unsupported
   rules produce the patterned unavailable state, without inferred permission.
2. Tests show identical source snapshots, run IDs, seeds, clocks, data sources and
   modeled outcomes before/after toggling; overlay state stays presentation-only.
3. Focused normal-entry browser interactions for enabled and missing cases,
   keyboard and mobile touch, reduced motion, hide/reopen and selection cleanup.
   Verify through-building visibility with a reviewed screenshot or a measured
   visual receipt. Cover the static fallback or explicitly expose its limitation.
4. Run affected repository tests and any applicable module type checks, review
   adjacent pending PR revisions and compare the final executable paths with the
   source/units contract. Update the issue record with actual receipts.
